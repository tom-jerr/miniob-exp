#01 P0 · 内存安全 Compaction

LeveledCompactionPicker 悬垂 string_view（ASan stack-use-after-scope）

▶
现象

开启 ASan 运行 ob_compaction_test 时，在 ob_compaction_picker.cpp:107 触发 ERROR: AddressSanitizer: stack-use-after-scope 崩溃。

根因分析

ObSSTable::first_key() 与 last_key() 返回的是按值拷贝的临时 std::string。代码中直接写成 string_view min_user_key = extract_user_key(sst->first_key());，完整表达式结束后临时 std::string 立即析构，导致 min_user_key 成为悬垂视图，在后续遍历 Li+1 层比较键区间时读取已释放栈内存。

解决方案

将 first_key() / last_key() 的返回值以及提取出的最小/最大用户键统一存为具名 std::string 持有所有权，再构造 string_view 参与比较。

std::string fk0 = sst->first_key();
std::string lk0 = sst->last_key();
std::string min_user_key(extract_user_key(fk0));
std::string max_user_key(extract_user_key(lk0));
涉及文件：src/oblsm/compaction/ob_compaction_picker.cpp
#02 P0 · 崩溃/泄漏 文件描述符

10 万级 ob_compaction_test 段错误：重复 open_file() 耗尽 FD（EMFILE）

▶
现象

写入约 100k 记录并频繁触发多轮 Flush / Compaction 时，程序在 ObFileWriter::open_file() 处以 SEGV on unknown address 0x000000000098 崩溃。

根因分析

地址 0x98 对应 this == nullptr 的成员偏移，说明 ObFileWriter::create_file_writer() 返回了 nullptr（系统调用 open() 失败）。沿调用链回溯发现：ObFileReader::create_file_reader() 内部已经打开了文件，而 ObSSTable::init() 又重复调用了一次 file_reader_->open_file()，直接覆写了 fd_ 却未关闭旧 fd，导致每生成一个 SSTable 泄漏 1 个文件描述符；当进程打开文件数触达 ulimit -n（1024）时，新 SSTable 写入因 EMFILE 失败返回空指针。

解决方案
  • 删除 ObSSTable::init() 中冗余的 file_reader_->open_file() 调用；
  • 在 ObSSTableBuilder::open() 中对 file_writer_ == nullptr 增加保护并返回 RC::IOERR_OPEN；
  • 在 try_major_compaction() 递归触发下一轮压缩前先清空 picked_sstables，尽早释放旧 SSTable 的 shared_ptr 与文件句柄。
涉及文件：src/oblsm/table/ob_sstable.cpp src/oblsm/table/ob_sstable_builder.cpp src/oblsm/ob_lsm_impl.cpp
#03 P0 · 并发竞态 POSIX unlink

10 万并发读写 ConcurrentPutAndGetTest/4 段错误：提前 close(fd) 破坏并发读快照

▶
现象

多线程并发写入 + 读取触发后台 Compaction 时，读线程在 ObBlock::size() 处空指针解引用（0x28）崩溃；此外 check_compaction 偶尔读到未收敛的层级快照。

根因分析

后台 Compaction 完成后调用 ObSSTable::remove()，原先在其内部主动调用了 file_reader_->close_file() 将 fd_ 关闭并置为 -1。但此时并发读线程仍持有旧版 shared_ptr<ObSSTable>，其 TableIterator 继续执行 ::pread(fd_, ...) 失败，返回空 ObBlock 指针导致崩溃。同时 get_sstables() 未同步等待后台 Compaction 结束。

解决方案
  • 利用 POSIX unlink 语义：ObSSTable::remove() 仅调用 std::filesystem::remove(file_name_) 删除目录项，绝不主动关闭 fd_；仍在读该文件的线程继续通过有效 fd_ 安全 pread，直到最后一个 shared_ptr<ObSSTable> 析构时由 ~ObFileReader() 自动 close(fd_) 并由内核回收 inode；
  • 在 ObLsmImpl::get_sstables() 中通过条件变量 cv_.wait 等待后台 Compaction 完成并由工作线程 notify_all()。

#04 P1 · 持久化恢复 Manifest

ob_lsm_manifest_test 崩溃：ObFileReader 缓存陈旧 file_size_

▶
现象

manifest_without_currentfile:86 测试在读取刚写入的 Manifest 记录时读到 0 字节，后续反序列化空指针崩溃。

根因分析

为了减少系统调用，曾在 ObFileReader::open_file() 中一次性缓存 file_size_。但 ObManifest 的使用模式是：先打开 reader_（此时文件大小为 0），再通过独立的 writer_ 持续追加写入记录，随后直接用同一个 reader_ 读取最新内容——静态缓存的 file_size_ 永远停留在 0。

将 ObFileReader::file_size() 改为基于 ::fstat(fd_, &st) 动态获取长度：既能实时感知追加写入后的最新大小，又在文件被 unlink 后依然对已打开的 fd_ 有效（优于基于路径的 stat()）。

#05 P1 · 并发迭代器 MemTable B+Tree

bplus_tree_concurrent_insert_and_scan 重复键（actual: 2003 vs 2003）

▶
现象

多线程并发向 ObMemBPlusTree 插入数据同时执行顺序扫描，迭代器校验单调严格递增时报错：连续两次返回键 2003。

根因分析

游标漂移（Cursor Drift）：迭代器在 key() 返回后释放了树级 shared_lock；在调用 next() 重新加锁的窗口期内，写线程向同一叶子节点插入了一个小于 2003 的新键，导致 leaf_->keys 数组整体右移 1 位。随后 next() 单纯执行 idx_++，恰好再次命中右移后的 2003。

解决方案

在 ObMemBPlusTree::Iterator 内缓存上一次访问的 current_key_：next() 重新持锁后，先走 O(1) 快速路径判断当前位置是否仍为 current_key_；若发生位移或节点分裂，则回退使用 std::upper_bound 重新定位首个严格大于 current_key_ 的键，确保并发扫描严格单调不重不漏。

涉及文件：src/oblsm/memtable/ob_bplus_tree_mem.h

#07 P0 · 数据丢失/死锁 MVCC Rollback & GC

mvcc_concurrency_test gc_stress 丢失已提交行 id=2，以及误加锁引发 sync; 超时

▶
现象
  • 原始现象：高并发回滚 + GC 压测（gc_stress）中，已明确收到 COMMIT SUCCESS 的记录 (id=2, v=8) 神秘消失；
  • 中途踩坑：尝试在 MvccTrx 的 DML/提交/回滚路径加 shared_lock(checkpoint_gate()) 后，导致 sync; 命令 10 秒超时。
根因分析
  • 数据丢失竞态时序：MvccTrx::rollback() 先调用 abort_trx(trx_id_) 公开标记事务已中止，之后才遍历 operations_ 逐条删除已插入的 RID；更致命的是，检查记录归属的 begin_xid != -trx_id_ 仅在 if (recovering_) 分支生效！于是并发 MvccGc::collect() 看到 ABORTED 后立刻清理了该 RID；紧接着另一个并发事务复用该空槽 RID 写入并提交了 (id=2, v=8)；最后慢线程的 rollback() 执行无条件 delete_record(rid)，一刀误删了刚提交的新记录！
  • sync; 超时根因：Db::sync() 在全库 fsync_all() 期间持有 unique_lock(checkpoint_gate())，与高频 DML 争抢 shared_mutex 导致长尾阻塞与写者饥饿。
解决方案
  • 放弃在 MvccTrx 中加 checkpoint_gate() 锁；
  • 调整 MvccTrx::rollback() 顺序：先完成所有 operations_ 的 Undo 清理，最后再调用 abort_trx(trx_id_); started_ = false;，确保 GC 不会与正在 Undo 的事务并发抢占同一 RID；
  • 将 Operation::Type::INSERT 撤回时的 begin_xid != -trx_id_ 归属校验改为无条件执行（双保险防御 RID 复用）。修复后 mvcc_concurrency_test.py 全部并发用例 100% 通过。
涉及文件：src/observer/storage/trx/mvcc_trx.cpp test/case/concurrency/mvcc_concurrency_test.py
#08 P0 · 事务隔离/UPDATE LSM 二级索引

▶
现象

#09 P1 · 快照边界 Sequence Number

LSM 事务序号 0-based 导致空库 Snapshot Isolation 边界击穿

▶
现象

空库启动事务 T1（快照时间戳 ts_ = 0），随后 T2 插入并提交首条记录后，T1 竟然能读到 T2 新提交的数据，破坏了快照隔离（SI）。

根因分析

seq_ 初始为 0，原先 put() 使用 seq_.fetch_add(1)（0-based），使第一次提交分配到了 seq = 0。由于可见性判断为 entry_seq <= ts_，0 <= 0 成立导致 T1 看到了在它之后提交的 T2！

解决方案

统一 ObLsmImpl::put() 与 batch_put() 采用 1-based 分配（seq_.fetch_add(1) + 1），严格维护不变量：seq_.load() 始终等于「最新已提交版本号」。空库开启的事务 ts_ = 0，任何后续提交都有 seq >= 1 > ts_，彻底消除边界漏洞，OCC 写冲突检测 latest_seq > ts_ 也完全精确。

涉及文件：src/oblsm/ob_lsm_impl.cpp src/oblsm/ob_lsm_transaction.cpp

#12 P0 · 双层隐蔽 Bug Parser & TPC-C

select sum(c_balance) from customer; 返回 NULL：负数字面量解析失败 + 测试脚本静默吞错

▶
现象

聚合函数上线后运行 miniob_tpcc.py --engine lsm --trx lsm，数据加载“顺利完成”，200 笔事务跑完且 CC1~CC6 全通过，却在最后一行快照查询 select sum(c_balance) from customer; 时抛出 ValueError: could not convert string to float: 'NULL'！

  • 加固 miniob_tpcc.py 的 exec_ok()、query_rows()、run_sql_in_trx()：任何包含 "FAILED TO PARSE" 的响应立即抛出 RuntimeError，杜绝静默吞错。

前者在全是 TEST_F 的测试文件中残留了 INSTANTIATE_TEST_SUITE_P；后者调用 db->init 时将 trx_kit_name（"lsm"）与 log_handler_name（"vacuous"）两个字符串参数位置写反。

解决方案

删除无用的参数化实例化宏并修正 db->init 参数顺序。修复后 oblsm 相关 72 项 GTest（含 ASan 与并发压测）及全库 ctest 全部通过。

涉及文件：unittest/oblsm/ob_lsm_transaction_test.cpp unittest/observer/lsm_table_engine_test.cpp

核心工程经验沉淀（Checklist）

  1. 资源生命周期与并发读解耦（POSIX unlink 原则）：在 LSM-Tree 等只读文件架构中，Compaction 删除旧 SSTable 只能 unlink 目录项，绝不能抢先 close(fd)；让 shared_ptr 引用计数和 RAII 析构器自然管理文件描述符的关闭时机，并用 fstat(fd) 替代静态大小缓存。
  2. MVCC 状态公开必须晚于 Undo 完成：事务回滚时，必须在所有记录清理完成后才对外公开 ABORTED 状态，且 Undo 操作必须校验记录当前的事务归属标记（begin_xid == -trx_id），防止与 GC 和 RID 复用交织造成误删已提交数据。
  3. string_view 严禁绑定按值返回的临时对象：始终在 Debug 构建开启 AddressSanitizer（ASan）跑满高并发单测，能在毫秒级揪出 stack-use-after-scope 与越界访问。
  4. 语法扩展与 Bison 零冲突设计：在已有 '-' expression %prec UMINUS 的文法中支持负数字面量时，不要直接修改 expression 引用的 value，而是拆分独立的 signed_value 给 INSERT/UPDATE/WHERE/SET 使用，天然保证 0 shift/reduce 冲突。
  5. 测试断言必须拒绝静默失败，善用跨引擎确定性摘要：端到端 SQL 脚本必须同时拦截 FAILURE 与 Failed to parse sql；使用相同随机种子在 lsm+lsm 与 heap+mvcc 上比对最终状态哈希（321cebcfaac7f6ad），是验证新存储引擎语义等价性的最强金标准。
